# 生产图片管线：统一验收与发布契约

状态：用户已确认首次人工审核并授权全量部署；实现与本地集成验证完成，正在执行上线核验。此文件不将未发生的真实人工批准或外部发布计为通过。

## 1. 目标与边界

目标不是承诺任意 PDF 都能自动裁对，而是：**未验收的图片不能被当成可发布素材；同一篇文章的公众号与各语言 Blog 使用同一份已验收图片包。**

自动抽图只产生候选。规则检查只能提供机器证据，不能单独证明图号、论文归属、科学面板完整性正确。模型也不能仅凭自报置信度把候选升级为合格图。

本轮不重写文案、不批量覆盖历史文章、不重新发送历史发布通知；4-3、4-4 的暂停保持不变。公众号依旧只进入草稿箱，不自动群发。用户已确认：每篇首次人工确认配图，随后自动多语言发布；未获确认前不发生外部发布写入。

## 2. 本轮证据与根因

2026-10-16 对生产 `image-quality-ef377ff` 的只读盘点：

| --- | --- | --- |

| 已生成正文 / 元数据 | 44 / 44 | 均未保存生成时 `source_pdf_sha256`；不能事后自动补值并称为验证过 |

| 24 份当前来源报告的候选图 | 145 张 | 不是 145 张已审核图片，也不等于最终正文插图数量 |
| 报告必需图号 / 缺图 | 68 / 6 | 6 个缺图均来自已暂停的 4-3、4-4；报告无缺图不代表图片内容正确 |

盘点证明的是证据缺口，不是 44 篇文章全部错误。旧文档的 15 份 PDF、80 个策略结果是历史样本记录，不是本轮全链路验收结果。

这里的 44 是 `outputs/jobs/*/article.md` 文件数，不等于已发布/当前有效文章数量。离线工具首次实扫同样覆盖这 44 份产物：41 份缺少完整证据，另 3 份还存在引用或文件一致性问题（2-1 引用与报告不一致、2-6 不同图号共用相同字节、4-9 引用和图像尺寸与旧报告不一致）。这些发现仍需结合历史版本核查，不能直接认定线上当前页面错误。完整只读结果保存在 `runtime/figure-audits/2026-10-16-baseline.json`，未修改任何生产数据。

当前结构性缺口：

1. `utils/figure_quality.py::filter_candidates` 检查尺寸、文字条纹、边界与重复等，但没有确认裁图像素和图号确实对应指定论文、页码、区域，也没有证明全部面板完整。
2. `batch_processor.py::_article_source_binding` 对旧正文仅记录 `legacy_unbound` 后继续；人工图片池的 `reviewed=true` 也未绑定完整图号/页码/裁框映射。
3. `_resolve_job_figures` 的候选和报告是可变文件。Blog 各语言、公众号与修复入口重新解析；现有锁按语言或操作区分，不能防止共同缓存同时变化。
4. `auto_blog_tasks` 只绑定中文正文哈希，不绑定 PDF 和图片包；因此同一次自动发布可能用到不同图片版本。
5. 当前公网图片探测只读前 1024 字节，不能证明整图可解码；公开页面 URL 可访问也不等于正文与图片落地正确。

## 3. 统一处理流程

```text
源 PDF + 基准正文版本
        ↓
候选抽图（独立临时目录，保留原页/图注/边界）
        ↓
结构检查 + 来源/图号/完整性验收
        ↓
冻结图片包 bundle_id
        ├── 公众号正文 + 独立适配封面
        └── 中文及其他语言 Blog
                    ↓
              平台回读与公开落地验证 → 完成状态 / 发布通知
```

发布端不再调用抽图器，也不自行选择首个可用图。图包冻结前的策略回退只用于找候选，不能绕过来源冲突或审核拒绝。

### 3.1 不可变图片包

包的内容身份至少绑定：

- `schema_version`、验收策略版本、抽取器版本。
- `job_pk` / `job_id` / 业务线、源 PDF SHA-256、基准正文 SHA-256。
- 源论文标识（标题/DOI 等可用证据）、身份核对依据和该论文在 PDF 中的页范围；同页多论文还需允许/排除区域。合刊中的同一个 PDF 哈希与 Figure 1 仍不足以确定论文归属。
- 正文实际图片引用序列（含重复引用）与去重图号清单；不能只相信旧报告的 `required`。
- 每张图的图号、普通/扩展图类别、图注、原文页码、PDF 坐标、像素尺寸、文件 SHA-256、来源类型。
- 封面源图及适配策略；正文图与封面衍生图分开保存，不因封面比例裁掉科研面板。

对规范化清单计算 `bundle_id`，文件复制到内容寻址的专用目录。清单中的每个审核相关字段改变都产生新 ID，不能保留旧 `reviewed=true`。包中路径只允许引用本包普通文件，拒绝越界路径和符号链接；文件完整解码、哈希和尺寸必须一致。

提取在独立临时目录进行；先完成并校验全部文件，再原子提交包。消费者不得读半成品。正文和 PDF 在构建前后都复核哈希。失败保留独立诊断，不污染现有包。旧缓存可以提供候选，不能自动成为合格包。

### 3.2 验收状态与权限

独立图片状态：`candidate` → `needs_review` → `approved`；结构损坏为 `blocked`。批准可撤销，源稿改变后旧批准不再适用于新版本。

- 硬性错误：文件损坏、来源哈希变化、缺必需图、同图冒充不同图号、越界路径、无效页码/裁框。必须修正，不能点击忽略后发布。
- 语义审核：论文归属、图号对应、全部面板/标签/坐标轴是否完整、是否误含正文或图注、封面是否可接受。展示原文整页与裁图对照，不只展示缩略图。
- 审核记录单独保存审核者身份、时间、`bundle_id`、明确确认项与备注。批准必须来自已有授权用户，不能由文件内布尔值或抽图器自我声明代替。
- 审核接口受现有业务线权限约束，拒绝批准陈旧的候选 ID；看板显示具体阻断原因，而不是普通“发布失败”。
- 本轮无图文章保持阻断，不提供“允许无图”放行入口；不能把抽图失败转为无图成功。

**已确认的业务选择：**每篇文章首次由人工一次确认图片包；此后公众号与所有语言继续自动处理，无需逐语言审核。图片包变化需重新确认。不存在基于当前规则分数自动批准的旁路。

仅更改裁图阈值、换更大模型、让同一个模型自行复核，都不能取代这个准入边界。

### 3.3 所有消费者钉住同一版本

| 入口 | 改造约束 |
| --- | --- |
| `_run_one_job` / `_publish_chinese_blog` / `_distribute_one` | 首次外部写入前取得批准包；现有中文 Blog 发布早于公众号投放，门禁不能只放在公众号函数内；正文与封面来自同包 |
| Blog `publish` / `_render_with_images` | 只消费指定包，验证译稿图号与基准序列一致，不再调用提取器 |
| `auto_blog.enqueue` / `_process` | 任务固定 `bundle_id`，重启/重试不切换到“最新包”；来源改变需新任务 |
| Blog / 公众号图片修复 | 同样消费批准包，保留备份、并发变更检查和字段回读；不允许维修入口绕过审核 |
| 飞书完成通知 | 通知钉住预期 `bundle_id` 和目标语言集合；对应投放回执全部验证通过才发送；历史补图不重置已发送记录 |

图片包清单与独立审核记录按现有大产物落盘约定存放，数据库增加任务/译文/发布回执的包引用；现有 `publish_blocked` 文案质量闸保持独立。自动任务幂等键包含图包版本，否则只换图片不换正文时旧 `done` 记录会被误复用。历史任务的包字段为空时标为历史未绑定，不批量补成最新包。SQLite 队列唯一键迁移在事务中保留旧表备份并校验行数，不删除旧记录。

锁统一以 job 为图片版本边界。发布、批准/撤销、换源等关键动作使用相同顺序：**job 锁 → 语言/平台锁**；禁止现有语言锁持有者再反向等待 job 锁。图片构建和业务发布的锁职责分开，原子提交后文件只读。最小实现可按 job 串行发布，优先可靠性，不引入不必要的分布式协调。

这要求同步迁移 `auto_blog._process`、`@serialized_version`、公众号正常投放及维修入口的外层锁，不能只在发布函数内部加锁。公众号正常投放与维修必须使用同一目标锁；数据库事务保持短小，不在事务内等待文件锁或调用外部网络。

自动 worker 全局锁可处于最外层；`kick` 保持非阻塞，禁止持有 job 锁时阻塞等待 worker 锁。

### 3.4 发布验证与异常恢复

- 上传前验证图包和本地完整图；上传后有大小上限、超时的全量读取与解码，比较尺寸和预期内容，不只读文件头。
- 未配置变换的原始资产要求完整 SHA 一致。仅对明确记录的 CDN 重编码路径，使用经验证的内容比对规则与尺寸检查替代字节相等；未知变换不得自动豁免。
- CMS / 微信回读核对正文图片清单、封面和保留字段。Blog 额外验证公开页面实际包含目标图并可加载；公众号草稿完成不写成公众号公开发布。
- 微信宽图封面按完整裁框回读验证；方形缩略预览未纳入本轮人工审核，回执明确标为 `not_reviewed`，不得据宽图通过宣称方形预览也已验收。源 PDF 上传使用冻结快照；既有公网 PDF 探测不是整文件 SHA 核验。
- 外部接口调用成功但回读失败时记录“落地待核对”，保存目标 ID 和期望版本，不自动重建重复文章，也不发送“全部发布成功”。
- 本地与远端不具备跨系统事务；明确记录尝试、结果和回执，恢复时先查目标再决定重试。不声称能够完全避免远端写入后瞬时故障。

## 4. 历史迁移与回归基线

1. 只读盘点全部 44 篇正文，包括失败、无图、缺源文件记录；分母不得只选成功样本。
2. 以现有 24 份 PDF 建立固定输入清单，记录 SHA、页数、版式类别。19 份找不到当前原文的报告单列待找回，不凭现存图片反推来源通过。
3. 两篇本轮故障、JEM 5-3、NEJM 合刊、EMBO 跨页图注，以及旧版多层页眉、矢量图、整图 raster、扩展图、图文混排都纳入。没有实际样本的扫描件、旋转页等类别明确记为未覆盖，不能写“已支持”。
4. 金标准由逐图原页对照确定正确图号与边界；不能拿当前抽图器输出自动生成标准答案。保留独立测试样本，防止只针对已见错误调整规则。
5. 运行冷缓存和暖缓存两轮；同时测源文件/正文/图片/图号修改、并发语言发布、进程中断、失败重试、CDN 重编码、回读失败。
6. 历史结果分类为证据不足、结构错误、待语义审核、已审核，不把 `missing=[]` 计作正确率。错误样本、未覆盖类别、漏检与误拦均计入报告。
7. 历史已发布内容先只读审计。需替换的逐篇生成预览与备份清单，再按确认范围修复；不得自动覆盖人工修改过的文案、封面和其他字段。

建议初始分组为 14 份人工定标、10 份独立留出影子集，覆盖全部 24 份现存 PDF。14 份包括 NEJM、Targeted AAV、JEM 5-3、4-9、4-7、4-8、4-1、CBLN1、4-5、ALPK3、5-1、Intravenous、4-3、4-4。这是待实施的评估安排，不是已完成的金标准；当前 76 张和留出组 69 张历史候选均不能直接作正确答案。

`scripts/audit_figure_artifacts.py` 是离线证据审计入口：不启动抽图、不调用网络、不修改现有产物。其报告不是语义审核批准，也不是公开页面验收。

## 5. 发布前必须满足的验收标准

- 未批准、来源变化、图片变化或字段映射变化的包，所有发布/维修入口均在外部写入前阻断。
- 公众号、中文和其他语言的发布回执引用同一 `bundle_id`，不会因重试、重启或算法更新重新猜图。
- 并发构建、发布与审核不会读到半包，不死锁；故障恢复不重复建文章或重复通知。
- 金标准样本中的误配图、图注当图片、裁掉面板等负例不得自动放行；无法确认的样本明确待审。
- 旧数据未绑定时不伪造批准，不自动回填当前 PDF 哈希冒充生成时证据。
- 外部写入、回读、公开渲染验收分开记录；单元测试数量和 HTTP 200 不能作为生产视觉验收的替代。

部署分阶段：离线影子评估 → 完整门禁/界面/数据迁移测试 → 小范围可回滚试运行 → 用户确认后扩大。发布前检查生产任务空闲；记录新旧代码和数据兼容性。回滚不能重新放开已经被明确阻断的素材；不得为恢复吞吐量关闭审核门禁。

回滚只允许切回兼容图包门禁的版本。若必须退回不识别门禁的旧代码，先暂停/隔离发布 worker 和所有外部写入口，再恢复只读和生成能力；不能只切换旧版本后让旧 worker 自动恢复发布。

历史空 `bundle_id` 不具备新发布资格；回滚不倒退审核记录、不覆盖部署后生成的发布回执。

## 7. 审核页失败恢复

业务线快捷链接只提供查看身份。需要批准时，点击“登录 GM-LAB 并返回本篇审核”，经正式入口登录后回到当前文章；快捷链接显示的默认业务用户名不作为审核身份。

候选生成和继续发布按本篇文章的准确任务编号查询状态，不使用全局最新任务替代。状态查询不启动发布 worker；请求超时会提示刷新核对，并保留待核对任务。明确失败后显示阻断原因、结束等待并恢复候选生成按钮。未知异常只对业务页面显示诊断编号，完整异常保留在后台日志。

图注解析只在真实分栏间距处拆出右栏题注，避免把连续句子里的“Fig. 2”等交叉引用识别为独立图注。不同原页/区域真实共享同一图号时，重复图号检查仍然阻断候选，不能自动选择首张。

去除出版社页眉时，若坐标文字跨过图形对象并集的下边界，裁框保留该文字的完整边界；不引入起始位置位于图框下方的图注。各抽取器的缓存版本随此几何行为一并更新。
